- **Step 4 part 2: diagnosis and one retry.**
  - **What the 10 production calls showed** (README sample, ~3 s apart, after `c4510f2`): 1× `200`, 5× `504` (our 15 s timeout), 4× `502` with `detail = {"providerStatus": 503, "providerErrorStatus": "UNAVAILABLE"}`. So the failures are **transient provider unavailability**, not a rejected request setting and not something on our side.
  - **Retry:** exactly one retry, and only for provider `500/502/503/504` (`isRetryableStatus`). Never for `429`, other `4xx`, timeouts, network errors, or malformed model output. The model and every request setting are unchanged.
  - **Timeout:** `REQUEST_TIMEOUT_MS` raised 15 s → **30 s per attempt** so a slow first attempt can still recover. Verified against Vercel's docs: Hobby's default **and maximum** function duration is **300 s** (vercel.com/docs/functions/limitations#max-duration — table row "Hobby | 300s (5 minutes) | 300s (5 minutes)"), configured on App Router routes with a named `maxDuration` export (vercel.com/docs/functions/configuring-functions/duration). This route exports **`maxDuration = 90`**: 2 × 30 s attempts + a 10 s overhead allowance = 70 s, leaving 20 s of headroom so Vercel's own 504 never pre-empts our JSON error. `maxDuration` must be a literal (Next.js statically analyses segment config — a computed value failed the build), so `test/agent.test.ts` asserts the literal matches `MAX_FUNCTION_DURATION_S` and that `RETRY_BUDGET_MS` (70 s) fits inside it and inside the 300 s Hobby limit.
  - **SPEC.md:** "no automatic retries" replaced with the one-retry rule above.
  - **Tests:** 11 new stubbed tests (43 total, all passing) — each retryable status retried once then `200`; two `503`s → `502` after exactly two calls; the retried result still goes through the evidence check (an invented quote is still downgraded); `429` not retried; a provider `400` not retried; a network error not retried; `isRetryableStatus` covers exactly 500/502/503/504; and the retry/timeout budget fits inside `maxDuration`.
  - **Measured effect (same 10 calls, README sample, ~3 s apart, after `09a1b59`):** **8/10 succeeded** (before: **1/10**), still 2× `504`. With 30 s attempts, one call that would have failed at 15 s now succeeds in 22 s (call 1), and one succeeded at 29.7 s. Cause of the remaining failures: the retry fires only on a *returned* 5xx; when Google simply doesn't answer, our own timeout ends the attempt and timeouts are (correctly) not retried.
